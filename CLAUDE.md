# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A static, multi-page marketing site for **RamalVirtual Telecom** (cloud PABX/telephony for businesses), hosted on **Vercel**. Each page is one self-contained HTML file — plain HTML + inline `<style>` + inline `<script>`, no build step, no dependencies, no framework, no shared/templated partials.

- `index.html` — the homepage. Hero, trust strip, problem cards, solution, plans, "how it works", client logos, FAQ, contact form.
- `funcionalidades.html` — the "Funcionalidades" page (features/comparison page), reachable at `/funcionalidades` (see "Deployment / clean URLs" below). Hero, a full feature-comparison table (online vs. assisted contracting), an apps/devices section, an AI section with an animated "call finished" demo card, and an integrations/support two-column section.
- Both pages **duplicate** the header, mobile nav panel, floating WhatsApp widget, footer, and the full `:root`/base CSS — there is no templating or includes mechanism. When changing shared chrome (header nav, footer links, the WhatsApp number, brand-name copy, button styles, breakpoint values), **grep across both files and apply the same edit to both** rather than editing just the one you're looking at. This has already caused one visible regression (header spacing silently diverged between the two files after `funcionalidades.html` was created — see project history).
- `vercel.json` — `{ "cleanUrls": true, "trailingSlash": false }`. This is why every internal link in both pages is written without the `.html` extension (e.g. `href="/funcionalidades"`, `href="/#contato"`) — see "Deployment / clean URLs" below.
- `Ramal Virtual LP.dc.html` + `support.js` — the **original** file this project was converted from (a Claude Design "canvas" file with a custom templating runtime: `{{ }}` bindings, `sc-if`/`sc-for`, `style-hover` attributes). It is legacy source material only, kept for reference. Do not edit it expecting it to affect the live site, and do not treat its templating syntax as valid HTML.
- `uploads/` — all images referenced by the HTML pages (logos, product photos, client logos in `uploads/clientes/`, partner logos in `uploads/parceiros/`). Filenames are inconsistent (spaces, mixed case, some `.jpg.jpeg` double extensions) because many were carried over from the original canvas project — **check actual pixel dimensions before trusting a filename or an existing `width`/`height` attribute**; several images in this repo are secretly PNGs with transparency saved under a `.jpeg` extension, and at least two had `width`/`height` attributes that didn't match the real file, causing visible stretching until fixed.

## Deployment / clean URLs

Hosted on Vercel with `cleanUrls: true` (`vercel.json`), so pages are served without their `.html` extension (`/funcionalidades`, not `/funcionalidades.html`) and Vercel 308-redirects the `.html` URL to the clean one. Every internal `href` in both pages must therefore be extension-less and root-relative: `/`, `/funcionalidades`, `/#contato`, `/#solucao`, etc. — never `index.html` or `funcionalidades.html`. `serve.ps1` (the local dev server) replicates this: if a requested path has no file extension and no exact file match, it retries with `.html` appended, so `/funcionalidades` resolves locally the same way it does on Vercel.

## Running / previewing locally

There is no build command — just open `index.html`. For anything beyond a static glance (testing responsive behavior, verifying images load, running the FAQ/menu/form JS), serve the directory over HTTP rather than opening the file directly:

- This machine has **no working Python** (`python`/`py` resolve to the Windows Store stub, not a real interpreter) and no Node — `python -m http.server` and `npx serve` will not work here.
- Use the PowerShell `HttpListener` script already in the repo: `serve.ps1` (port 8642), launched via the `.claude/launch.json` config `static-site` (`powershell.exe -NoProfile -ExecutionPolicy Bypass -File serve.ps1`) — the default execution policy blocks unsigned scripts, hence the `-ExecutionPolicy Bypass`.
- Opening `index.html` via a `file://` path in the in-app Browser preview tool renders it in a sandboxed "snapshot" mode that inlines everything as a `data:` URL — relative `uploads/...` image paths silently fail to resolve in that mode. Always serve over `http://localhost` when checking that images actually load.

## Architecture of index.html

`funcionalidades.html` follows the same three-part structure and the same four responsive breakpoints (1024/860/640/400px), and reuses `index.html`'s `:root` variables, button classes, header/footer/WhatsApp-widget markup and CSS verbatim (hand-copied — see the "duplicate chrome" warning above). It adds its own sections on top (comparison table, AI card, etc.) documented in the project history below rather than repeated here.

Single file, three parts in order:

1. **`<style>` in `<head>`** — CSS custom properties on `:root` for the palette (`--blue`, `--blue-dark`, `--cyan`, `--ink`, `--muted`, etc.), then component styles in source order (header, hero, strip, cards, plans, FAQ, contact form, footer, floating WhatsApp widget), then all responsive overrides grouped into three `@media` blocks at the bottom of the stylesheet:
   - `max-width:1024px` — tablet: single-column hero/sections, 2-col grids.
   - `max-width:860px` — where the header nav collapses into the hamburger menu.
   - `max-width:640px` — phone: single-column everything, reduced hero-card/panel sizing, tighter paddings.
   - A `max-width:400px` block for the smallest phones.

   When a grid needs to collapse to fewer columns responsively, use `minmax(0,1fr)` tracks (not bare `1fr`) — bare `1fr` tracks let a wide child (e.g. an uppercase nowrap button label) blow out the grid and cause horizontal page overflow on narrow viewports. This has been the recurring bug class in this file; check `document.documentElement.scrollWidth` vs `clientWidth` at 320/375/414px after any grid/breakpoint change.

2. **Body markup** — semantic sections in reading order: sticky `<header>` → `<main id="top">` (hero, trust strip, problem cards, solution, plans, "how it works", client logos, FAQ, contact form) → `<footer>` → the floating WhatsApp widget (`.wa-float`, appended after `</main>`, not inside `<header>`).

   The mobile nav panel (`#mobilePanel`) is a **sibling of `<header>`**, not a child of it — `<header>` has `backdrop-filter`, which creates a new containing block and breaks `position:fixed` for any fixed-position descendant. Keep any future fixed/full-screen overlay outside of `<header>` for the same reason.

3. **`<script>` at the end of `<body>`**, one IIFE containing independent, self-contained behaviors — mobile menu toggle, FAQ accordion (data-driven from a `FAQ` array, single-item-open), contact form validation (client-side only, no backend — shows a success message on valid submit, does not actually send anywhere), and the floating WhatsApp bubble (auto-shows once via `sessionStorage`, dismissible).

### Floating WhatsApp widget (`.wa-float`)

Two parts: a pulsing round FAB (`#waFab`, links to `https://wa.me/551130900900`) and a greeting bubble (`#waBubble`) that auto-shows ~2.5s after load unless already dismissed this session (`sessionStorage` key `rv-wa-bubble-dismissed`). The bubble's avatar image is `uploads/perfil-ig.png` — swap the `<img>` `src` there (and its `width`/`height` attrs) if the profile picture changes.

The WhatsApp number `551130900900` and the `https://wa.me/...` link pattern now appear in many places across both pages (this widget, the header WhatsApp icon button, the mobile nav panel, and every "Seja Parceiro" link — see below), each one duplicated per file since there's no shared partial. If the number ever changes, grep both HTML files for `551130900900` and update every match.

**"Seja Parceiro" links** (header ghost button, mobile nav panel, footer "Acesso rápido" list — 3 spots per page × 2 pages = 6 total) don't go to `#contato`; they open `https://wa.me/551130900900?text=...` in a new tab with a pre-filled message ("Olá, vim pelo site e gostaria de saber mais sobre como ser um parceiro da RamalVirtual!", URL-encoded). Keep the encoded `text=` query param identical across all 6 when editing.

## User preferences

- Communicates in Brazilian Portuguese; respond in kind.
- Wants each page as **one self-contained HTML file** — no build tooling, no framework, no split CSS/JS files, no templating.
- Cares a lot about responsive correctness specifically at 320/375/414px (phone), 768/834px (tablet), and 1024/1440px (desktop) — check `scrollWidth` vs `clientWidth` at these widths after layout changes, don't just eyeball one size.
- Prefers changes to be actually verified (in-browser, via a local server) rather than assumed correct from reading the CSS — several bugs in this project's history (inline `style` overrides, wrong image aspect ratios) were invisible from source alone and only showed up when actually rendered.
- When an asset (image, logo) is needed, expects it to be provided as a file dropped into `uploads/` with a filename they give — do not search the broader filesystem for "probably the right image," that has surfaced unrelated personal files before.
- Prefers a plain-language summary of what changed at the end of each turn, not a restatement of the whole file.
- Wants every change committed and pushed to `origin` automatically after it's made — no need to ask each time (still use clear commit messages, and still ask before anything destructive like a force-push).
- Iterates on visual/motion additions by trying them live and reacting — an added animation or effect may get reverted outright in the very next message if it doesn't land well; don't over-invest in defending a first attempt.
- Brand name must always be written as **"RamalVirtual"** (one word, capital R and V), with feminine grammatical agreement ("a RamalVirtual", "da RamalVirtual") — never "Ramal Virtual" (two words) or "o Ramal Virtual". Applies to every page.
- The site is now multi-page (`index.html` + `funcionalidades.html`, more may follow), hosted on Vercel with clean URLs (no `.html` in links — see "Deployment / clean URLs"). Each page is still meant to stay a single self-contained HTML file with no shared partials, so any change to shared chrome (header/footer/WhatsApp number/breakpoints) needs to be applied to every page by hand — check for drift between files, it has already happened once (see project history #20).
